# PKQB 后期优化清单

> 本文档汇总项目中**当前阶段为求简单/够用而采用的策略**，以及后期条件成熟时的优化方向。
> 定位：不是缺陷清单，而是"技术债台账"——每项都是当时权衡后的合理选择，规模或需求变化后才需要动。
> RAG 数据隔离的完整设计说明与方案取舍在 `RagDataIsolationServiceImpl` 的 Javadoc 中（代码即文档），本文档第 2.4 节登记其优化条目。

---

## 一、安全类

### 1.1 配置文件明文密钥且已提交 Git ⚠️ 优先级最高

**现状**：`backend/src/main/resources/application.yml` 中硬编码了全部敏感配置，且 `.gitignore` 未排除该文件，意味着密钥已进入 Git 历史：

| 配置项 | 位置 | 风险 |
| --- | --- | --- |
| `jwt.secret` | application.yml L56 | token 签名密钥泄露 = 任何人可伪造任意用户身份 |
| `app.api-key.encrypt-secret` | L61 | 用户 API Key 的 AES 加密密钥泄露 = 库中所有密文可解密 |
| `minio.access-key/secret-key` | L65-66 | 对象存储完全失守 |
| `spring.datasource.password` | L14 | 数据库 root 密码明文 |
| Redis 地址 | L7 | 内网拓扑泄露 |

**优化方向**：
1. 立即：`.gitignore` 增加 `application.yml`，仓库中只保留 `application.example.yml`（占位符形式）；已提交的密钥全部轮换（JWT secret、MinIO 密码、DB 密码）。
2. 中期：敏感项改为环境变量注入（`${JWT_SECRET}` 形式），或接入配置中心（Nacos）/ 密钥管理服务（Vault、云 KMS）。
3. 若仓库已推送远端，需用 `git filter-repo` 清理历史或视为密钥已泄露处理。

### 1.2 JWT 单 Token 无刷新机制

**现状**：[JwtUtil.java](../backend/src/main/java/pkqb/util/JwtUtil.java) 只签发一种 token，有效期 7 天（`jwt.expiration: 604800000`）。登出时将 token 加入 Redis 黑名单（`token:blacklist:`），但无 refresh token、无密钥轮换机制。

**局限**：token 一旦泄露，在过期或手动登出前持续有效；7 天窗口较长。用户改密码后旧 token 也不会自动失效（除非登出）。

**优化方向**：access token（短，如 2h）+ refresh token（长，如 14d）双 token 机制；改密码/重置密码时主动使该用户所有 token 失效（黑名单按 userId 维度记录签发时间戳）。

### 1.3 无找回密码 / 邮箱验证通道

**现状**：用户表无邮箱字段，全系统无验证码/邮件发送能力。忘记密码的唯一途径是管理员在后台重置（[AdminUserServiceImpl.java](../backend/src/main/java/pkqb/service/impl/AdminUserServiceImpl.java) L171-183）。注册也无任何验证，用户名+学号即可开户。

**优化方向**：用户表加邮箱字段，注册/找回密码走邮箱验证码（spring-boot-starter-mail + Redis 存验证码，5 分钟有效期 + 发送频率限制）。学号场景也可对接学校统一认证（CAS/OAuth）。

### 1.4 用户 API Key 对称加密、密钥静态

**现状**：[ApiKeyEncryptor.java](../backend/src/main/java/pkqb/util/ApiKeyEncryptor.java) 使用 AES-GCM 加密用户 API Key 后落库，密钥来自配置文件单项 `app.api-key.encrypt-secret`，全系统共用且不可轮换。

**优化方向**：密钥迁移到 KMS；如需轮换，密文加版本前缀（`v1:...`），解密时按版本选密钥，后台任务惰性重加密。

### 1.5 生产环境 Swagger UI 默认开启

**现状**：application.yml 中 `springdoc.swagger-ui.enabled: true` 且无 profile 区分，生产部署后 `http://host:5555/swagger-ui.html` 暴露全部接口结构（含 `/api/admin/**`）。

**优化方向**：`application-prod.yml` 中关闭，或加管理层鉴权。

### 1.6 前端 token 存 localStorage

**现状**：学生端与管理端的 token 均存 `localStorage`（[request.ts](../frontend/src/api/request.ts) L64-70，admin-frontend 同构），axios 从 localStorage 取出放请求头。SSE 通知已改为 HttpOnly Cookie 认证，但主 REST 请求仍依赖 localStorage。

**局限**：任何 XSS 漏洞都可直接读走 token。当前 XSS 防护靠手写转义（见 1.7），属于"单层防线"。

**优化方向**：全面切换 HttpOnly Cookie 认证（后端已具备 Cookie 解析能力，见 JwtInterceptor），前端不再持有 token；同时需要补 CSRF 防护（SameSite=Strict 或 CSRF token）。

### 1.7 AI 消息渲染的手写 XSS 防护

**现状**：[AIChat.vue](../frontend/src/views/AIChat.vue) L261-270 先手写作 HTML 转义再交给 `marked` 渲染；[RAGChat.vue](../frontend/src/views/RAGChat.vue) L269-285 是更轻量的手写 Markdown 转换。

**局限**：手写转义难以覆盖所有边界（如 marked 对链接 `javascript:` 协议、HTML 块的处理随版本变化）。

**优化方向**：引入 DOMPurify，`DOMPurify.sanitize(marked.parse(text))` 作为唯一渲染入口，替换两处手写实现。

## 二、架构与扩展性

### 2.1 SSE 通知连接存单机内存

**现状**：[NotificationSseManager.java](../backend/src/main/java/pkqb/config/NotificationSseManager.java) L27-58 用 `ConcurrentHashMap<Long, CopyOnWriteArrayList<SseEmitter>>` 在 JVM 内存中维护连接。

**局限**：单实例部署下无问题；一旦水平扩展为多实例，用户连接落在哪个实例是随机的，通知发送方找不到其他实例上的连接；实例重启全部断连（靠浏览器自动重连缓解）。

**优化方向**：引入 Redis Pub/Sub 或消息队列做跨实例广播——每个实例订阅频道，收到消息后推给本地连接的用户。这是"单机 → 集群"改造中最先会撞墙的点。

### 2.2 Agent 会话记忆为堆内 TTL 实现

**现状**：官方 `MemorySaver` 的 checkpoint 永久驻留堆内存，项目用自定义 [TtlMemorySaver.java](../backend/src/main/java/pkqb/config/TtlMemorySaver.java) 记录最后活跃时间、淘汰 7 天不活跃会话。

**局限**：仍是堆内存储——会话多了占内存，重启全丢，多实例间不共享。用户刷新重进时若实例已重启，对话上下文丢失。

**优化方向**：pom.xml 已引入 `spring-ai-alibaba-starter-memory-redis`，切换为 `RedisSaver` 即可持久化并支持多实例，TtlMemorySaver 可整体下线。

### 2.3 管理端与学生端同应用部署

**现状**：按项目约束，管理端是同一 Spring Boot 应用内的 `admin` 包，靠 `AdminInterceptor` 校验 `role=1`。这在当前规模是刻意简化。

**局限**：管理端与学生端共享 JVM、连接池、限流维度；学生端流量高峰会影响管理操作；任一端的漏洞影响面相同。

**优化方向**：出现真实运维需求（独立发布节奏、独立权限审计、资源隔离）时再拆分服务；拆分成本低，因为代码已按包隔离、接口已按 `/api/admin/**` 隔离。

### 2.4 RAG 数据隔离的四个已知限制

完整设计论证（为何 classId 不进过滤路径、被放弃的"事件驱动回写"与"file 表快照列"两个方案）见 [RagDataIsolationServiceImpl.java](../backend/src/main/java/pkqb/service/impl/RagDataIsolationServiceImpl.java) 的 Javadoc 第二、四节，此处只列触发条件：

| 限制 | 触发条件 | 优化方向 |
| --- | --- | --- |
| 每次检索多一次 `select id from user where class_id=?` | 每次 AI 问答 | RAG 会话级缓存同班用户集合（接受缓存期内换班延迟） |
| 过滤表达式 `userId in [...]` 随班级人数线性变长 | 班级规模上百；千人级必须处理 | 切回"元数据快照 + 换班事件回写 + 定时对账"（原方案二） |
| `isPrivate` 变更回写向量库失败仅 `log.warn` | 回写失败时 | 加重试队列或对账任务 |
| 上线前入库的存量片段无 `userId`/`isPrivate` 元数据，检索不到 | 已存在 | 重新上传文件，或写一次性迁移脚本扫描 file 表补写元数据 |

### 2.5 文件下载权限模型较粗

**现状**：[FileServiceImpl.java](../backend/src/main/java/pkqb/service/impl/FileServiceImpl.java) L110-123 下载校验为"非本人 + 私有则拒绝"，即任何登录用户知道文件 ID 就能下载他人的班级公开文件。

**局限**：当前假设"登录用户 = 同校学生"成立时尚可接受；若未来开放注册或跨校，班级公开文件的边界就靠不住。

**优化方向**：下载时校验"文件非私有 → 下载者与上传者当前同班"，与 RAG 隔离语义对齐（单一事实源都是 user 表的 class_id）。

## 三、性能与可靠性

### 3.1 文件上传/下载整读内存，无分片

**现状**：
- 上传：[MinioService.java](../backend/src/main/java/pkqb/service/MinioService.java) 用 `putObject` 单对象上传；Spring multipart 上限 8MB（application.yml L19-22）。
- 下载：`getObject` 后整个读入 `ByteArrayOutputStream`（L88-107）。
- 知识库上传：[SpringAiAlibabaServiceImpl.java](../backend/src/main/java/pkqb/service/impl/SpringAiAlibabaServiceImpl.java) L243-289 同步把文件字节全部读入内存再交异步任务（为避免临时文件被清理的刻意取舍）。

**局限**：大文件（上百 MB 的 PDF）会撑高堆内存；弱网环境无断点续传。

**优化方向**：前端直传 MinIO（已有预签名 PUT 能力，`generatePresignedPutUrl`）+ 分片上传；下载改为流式写出响应体；按需调高 multipart 上限并配 Nginx `client_max_body_size`。

### 3.2 RAG 入库切分策略简单

**现状**：[SpringAiAlibabaServiceImpl.java](../backend/src/main/java/pkqb/service/impl/SpringAiAlibabaServiceImpl.java) L393-418：先按 `\n\n+` 分段，再 `TokenTextSplitter` 按 token 切，批量写入向量库。

**局限**：纯段落 + 固定 token 切分，会把语义紧密的内容（题目与选项、表格上下文）切断，影响召回质量。

**优化方向**：按文档结构切分（标题层级、表格整体保留）；对题目类文档用题型边界切分；评估加入 overlap 窗口。

### 3.3 限流为按天固定窗口

**现状**：[RateLimitServiceImpl.java](../backend/src/main/java/pkqb/service/impl/RateLimitServiceImpl.java) 用 Redis Lua 脚本按 `rate_limit:{feature}:{userId}:{date}` 计数，跨天重置；配置个人 API Key 的用户完全不受限。

**局限**：固定窗口在临界点有突刺（23:59 与 00:00 各用满额度）；按天粒度无法防短时爆发；"有个人 Key 不限流"意味着恶意用户配 Key 后无约束。

**优化方向**：滑动窗口或令牌桶（Redis + Lua 或 Bucket4j）；增加分钟级第二维度；个人 Key 用户改为更宽松但非无限的额度。

### 3.4 Agent 阈值均为硬编码

**现状**：[ReactAgentConfig.java](../backend/src/main/java/pkqb/config/ReactAgentConfig.java)：SummarizationHook 在 4000 tokens 触发、保留最近 20 条；ModelCallLimitHook 单轮工具调用上限 3 次；[RagAgentHook.java](../backend/src/main/java/pkqb/config/RagAgentHook.java) 中 `RECALL_TOP_K=20`、`SIMILARITY_THRESHOLD=0.5`、`RERANK_TOP_N=5`。

**局限**：不同模型（8k/32k/128k 上下文）共用同一套阈值；调参需改代码重启。

**优化方向**：抽到配置中心或 application.yml，按模型类型（个人模型/系统模型）分档；配合线上观测数据持续调优。

### 3.5 长聊天列表无虚拟滚动

**现状**：AIChat/RAGChat 的消息列表全量 DOM 渲染（流式输出已做增量推送 + 子组件 memo 优化，但历史消息多了之后 DOM 节点线性增长）。

**优化方向**：单会话消息量大的用户出现时，引入虚拟滚动（vue-virtual-scroller）或分页加载历史。

### 3.6 PWA 缓存策略为基础版

**现状**：[sw.js](../frontend/public/sw.js)：`/api/` 直接放行，静态资源 cacheFirst，导航 networkFirst；无版本化缓存清单、无过期清理。

**局限**：发新版后旧缓存可能长期不更新；缓存只增不减。

**优化方向**：接入 Workbox（构建期生成 precache manifest + 内容哈希），或至少给 CACHE_NAME 加版本号并在 activate 时清理旧缓存。

## 四、功能完整性与可观测性

### 4.1 SM-2 为简化版

**现状**：[WrongQuestionServiceImpl.java](../backend/src/main/java/pkqb/service/impl/WrongQuestionServiceImpl.java) L47-119：新增错题写死 `intervalDays=1`、`nextReviewDate=明天`、`masteryLevel=0`，复习时按简化规则更新 EF 与间隔。

**局限**：相对原版 SM-2 少了首次/二次复习的固定间隔序列（1 天、6 天）与更细的评分档位（原版 0-5 分，当前实际使用的评分粒度更粗）。

**优化方向**：对照 SuperMemo 原版补齐间隔序列与评分档位；或基于复习日志数据校准参数，演化为此场景定制算法。

### 4.2 审计日志只记成功操作

**现状**：[AuditLogAspect.java](../backend/src/main/java/pkqb/aspect/AuditLogAspect.java) 在 `point.proceed()` 正常返回后才写日志（`@Async` 异步落库）；业务方法抛异常时不留痕。

**局限**：失败的登录尝试、越权访问尝试（被拦截器拒绝）都不会进入审计表，而这恰是安全分析最关心的数据。

**优化方向**：切面改 try-catch 结构，异常也记录（带结果状态列）；登录失败、403 拒绝在拦截器层补审计点。

### 4.3 无监控与告警

**现状**：pom.xml 无 `spring-boot-starter-actuator`、无 micrometer/prometheus；线上状态只能靠日志文件。

**优化方向**：引入 actuator + Prometheus + Grafana 基础三件套；关键业务指标（AI 调用成功率、rerank 降级率、SSE 在线连接数、限流触发次数）埋点。

### 4.4 异步任务无持久化与重试

**现状**：知识库文档处理、题目解析等走 `@Async` 内存线程池，任务无持久化；进程重启时进行中的任务静默丢失，仅靠 SSE 通知"失败"或用户发现无结果。

**优化方向**：任务表落库（pending/running/done/failed）+ 启动时扫描恢复；任务量大后引入消息队列（RocketMQ）。

## 五、优化顺序建议

| 优先级 | 条目 | 理由 |
| --- | --- | --- |
| P0 | 1.1 密钥出 Git | 已发生的信息泄露面，与规模无关 |
| P0 | 1.5 生产关 Swagger | 一行配置 |
| P1 | 1.2 双 token、1.6 Cookie 认证、1.7 DOMPurify | 安全防线，用户量增长前完成 |
| P1 | 4.3 监控 | 没有观测就没有后续所有优化的依据 |
| P2 | 2.1 SSE 广播、2.2 RedisSaver | 决定是否需要多实例时再动 |
| P2 | 1.3 找回密码、4.2 审计补全 | 运营刚需出现时再做 |
| P3 | 2.4 RAG 规模优化、3.1 分片上传、3.2 切分策略 | 明确的触发条件（班级规模、文件大小、召回质量投诉） |
| P3 | 3.4 阈值外置、3.5 虚拟滚动、3.6 PWA、4.1 SM-2 | 体验调优，跟随用户反馈 |
